Your tests passed. Did the user journey?

UI Iceberg helps developers, QA teams, and AI coding agents find important journey conditions their tests missed, understand why a green result may be giving too much confidence, and choose the single best check to run next.

View UI Iceberg on GitHub

What UI Iceberg answers

What did we forget to test?
Map a critical user journey against the evidence that actually exists.
Why might green be misleading?
Spot cases where mocks, forced actions, retries, screenshots, or other shortcuts support a narrower conclusion than the team assumes.
What should we check next?
Recommend one bounded check that resolves the most important uncertainty.
What did the check prove?
Keep passing, failing, flaky, and unknown evidence distinct.

Why teams use it

Browser automation tools are good at executing the tests they are given. UI Iceberg focuses on the upstream problem: which journey conditions deserve evidence, whether the current evidence supports the conclusion being made, and which check would reduce the most important uncertainty next.

A team can have hundreds of green UI tests while still missing OTP returns, session expiry, duplicate submits, recovery after request failure, state loss after refresh, or a real integration boundary that the test suite replaced with a simulation.

For AI coding agents

UI Iceberg includes an MCP server. The preferred user-facing operation is review_claim, which returns what looks good, why the evidence may mislead, the best next check, and what remains unknown. More detailed evidence-governance operations remain available to agents without forcing that vocabulary onto the user.

What it is not

UI Iceberg does not replace Playwright, Selenium, Cypress, Katalon, accessibility scanners, or visual testing. Those tools execute or observe. UI Iceberg helps decide what deserves evidence and prevents a narrow green result from silently becoming a broader claim.

Common questions

Does a green test become a failure just because UI Iceberg finds a risk pattern?

No. A risk pattern says the evidence may support a narrower conclusion than expected. A targeted check is still required before claiming the product actually fails.

Does “no warning detected” mean the claim is safe?

No. Unchecked ways the evidence could mislead remain unknown until they are actually tested. UI Iceberg deliberately treats unknown as different from pass.

Is UI Iceberg production-ready?

Version 0.5 is experimental. Scenario planning, repository-aware evidence-risk detection, plain-language claim review, probe selection, Playwright scaffold generation, runtime reconciliation, deterministic receipts, and change-triggered rechecks are implemented. The project does not claim complete journey certification.
